# Карта переноса и совместимость

## Изученный источник

Прочитаны все пять модулей, контроллеры, DTO, сущности, сервисы, SecurityConfiguration, JWT, Liquibase-миграции и исходные тесты. Контрольные SHA-256 исходных файлов записаны до переноса в `monolith-source-hashes.json`. Исходные модели, контроллеры и DTO перенесены с заменой package и привязки схем PostgreSQL; исходный каталог не менялся.

## API

| Метод и путь | Успех | Сохранённые правила |
|---|---|---|
| POST `/api/auth/register` | 201 TokenResponse | email; пароль 8–72 символа; BCrypt; повтор email 409 |
| POST `/api/auth/login` | 200 TokenResponse | проверка пароля; JWT HS256, subject=email, 3600 секунд |
| GET `/api/cars` | 200 CarResponse[] | публичный каталог |
| GET `/api/cars/{id}` | 200 CarResponse | публичное чтение; неизвестный id 404 |
| POST `/api/cars` | 201 CarResponse | непустые brand/model/registrationNumber; длины 100/100/20; тариф >= 0; статус AVAILABLE |
| POST `/api/bookings/reserve` | 200 BookingResponse | положительный carId; только AVAILABLE; снимок тарифа; 404/409 |
| POST `/api/bookings/{id}/start` | 200 BookingResponse | RESERVED → ACTIVE, автомобиль RESERVED → IN_USE; 404/409 |
| POST `/api/bookings/{id}/finish` | 200 BookingResponse | ACTIVE → FINISHED, автомобиль IN_USE → AVAILABLE; событие; 404/409 |
| POST `/api/telemetry/location` | 204 без тела | существующий carId; latitude [-90,90], longitude [-180,180]; хранится последняя позиция |
| GET `/api/billing/history` | 200 BillingResponse[] | все счета по createdAt убыванию |
| POST `/api/billing/pay` | 200 BillingResponse | PENDING → PAID, paidAt; неизвестный счёт 404, повтор 409 |

Все изменяющие бизнес-операции и история счетов требуют JWT; auth, GET каталога, health и Swagger публичны. Как в исходнике, нет ролей администратора и фильтрации аренд/счетов по владельцу. Не добавлены несуществовавшие delete/update/cancel API или платёжный провайдер: оплата меняет статус записи.

Правила тарификации сохранены буквально: `seconds = Duration.between(startedAt, finishedAt).toSeconds()`, `hours = max(1, (seconds + 3599) / 3600)`, `amount = hourlyRate * hours`. Субсекунды отбрасываются так же, как в исходнике. Rate фиксируется при бронировании. Один счёт на bookingId. Начальные Tesla Model 3 / 320.00 и Toyota Corolla / 180.00 перенесены в Flyway.

## Границы и отказоустойчивость

- Fleet владеет каталогом и бронированием: прежняя локальная транзакция сохранена. Оптимистические версии защищают состояние. Проигравшая параллельная операция получает 409; все её изменения откатываются.
- Завершение и outbox находятся в одной MySQL-транзакции. Relay блокирует строки `FOR UPDATE SKIP LOCKED`, что позволяет запускать несколько экземпляров. Публикация помечается только после подтверждения брокера.
- Kafka topic `carsharing.booking-finished.v1`, ключ = bookingId. В JSON сохранены bookingId, carId, hourlyRate, startedAt, finishedAt. Нет Java type headers или межсервисной зависимости от JPA-сущностей.
- Billing проверяет bookingId и имеет уникальный индекс. Consumer group `billing-service-v1`, auto commit отключён, ack-mode=record. Ошибки повторяются; неисправимое сообщение требует вмешательства и блокирует продвижение обработки — оно не отбрасывается молча. Для промышленной эксплуатации следует добавить мониторинг lag/outbox, процедуру разбора неисправимых событий и архивирование опубликованного outbox.
- При одновременной оплате строка блокируется, второй запрос видит PAID и получает 409.
- Telemetry вызывает публичный GET fleet с таймаутами 3/5 секунд. При отсутствии машины возвращается прежний 404; недоступность удалённого сервиса — 503.

## Наблюдаемые особенности

1. Billing теперь согласуется асинхронно через Kafka: успешный finish не означает немедленную видимость счёта. Его необходимо дождаться в history. Формат finish остался прежним, без новых служебных состояний.
2. Сохранена особенность исходного Spring Security: анонимный невалидный register получает 401, поскольку error dispatch защищён; это проверено на запущенной неизменённой копии. Авторизованные невалидные бизнес-запросы получают 400.
3. Конкурентные конфликты fleet теперь явно возвращают 409 вместо необработанной ошибки optimistic locking. Последовательные бизнес-ошибки совпадают с монолитом.
4. Полный `/v3/api-docs` сохранён снимком контракта, а живые сервисные спецификации доступны по `/v3/api-docs/{fleet,identity,billing,telemetry}`. Сравнительный тест проверяет все paths и components.schemas.
5. Spring Modulith observability заменена отдельными Spring Boot health endpoints и логами сервисов. Это инфраструктурный механизм, а не бизнес-API.

## Данные

Каждый сервис подключён своим пользователем только к собственной БД. MySQL использует `utf8mb4_0900_bin`, чтобы сравнение email/регистрационных номеров оставалось регистрозависимым, как в PostgreSQL. Нет общего репозитория данных между сервисами. Fleet сохраняет объединение двух внутренних схем в одну БД для атомарности.

Перенесены структура и стартовые данные из миграций. Рабочая PostgreSQL-БД исходного приложения не читалась и её записи автоматически не импортировались. Для существующей рабочей базы нужен отдельный перенос снимка с сохранением id, BCrypt-хешей, UTC-меток и последующей проверкой AUTO_INCREMENT; нельзя повторно публиковать уже оплаченные аренды без сверки billing_records.
